# 权限、排查、轻量验证与安装

## 不要混淆四种隔离

| 能力 | 实际保证 | 不保证 |
|---|---|---|
| Run 任务目录和归属 | 固定 outputDirectory、登记产物时检查路径 | 自动截获 Python 任意文件操作 |
| DSH 模型 Session | 隔离请求上下文，记录模型往返和用量 | 限制磁盘写入 |
| subprocess / Windows Job Object | 托管子进程范围、退出与取消；此版本地实现按当前令牌启动 | 自动授予目录写权限或限制所有写入 |
| 额外 OS 文件沙箱 | 在具体平台机制支持的范围强制文件策略 | 自动修复所有 ACL、跨平台同等强度；Windows 实现也可能声明 partial |

Req 最终在用户明确接受后采用**受信任的受管 Python 后端**，不额外 confine；只读拒绝与路径/产物检查仍保留。这是本项目的权限取舍，不是 SDK 要求，也不是今后所有项目默认去掉沙箱的理由。

如要求 OS 强制写入边界，须保留受限执行并验证宿主正规授权；若正规机制不能给目录合法权限，仅修改业务插件可能无法完成。不能静默回退 full-access、改 ACL 或提权来制造“测试通过”。

### 若需拒绝只读会话

从正常调用链的真实 Agent/Session 解析 `sandboxPolicy.resolve({session})`，不要从 input 中相信 sessionId、cwd 或权限模式。SDK 回调此版不直接暴露 Agent；Req 使用工具执行拦截配合 AsyncLocalStorage 传递真实调用者，守卫按实际工具作用域注册并随插件撤销。

- 既检查业务入口，也考虑 Run 启动入口；只在业务函数里拒绝，Run 可能已创建请求目录。
- 只匹配本插件 toolId，不把其他 Run 业务一并拦住。宿主守卫只能收紧，不能强行放行被其他守卫拒绝的操作。
- 守卫若同步，异步 realpath/路径检查在业务层另做。核对真实路径、工作区后代关系和宿主对链接的规则；业务不允许用户自行指定输出根。
- **Remote 也要查路径。** 给 `sf_runtime_run_tool` 加 Tool 守卫，不代表 Remote 的 runTool 在创建目录前也经过该守卫。若承诺所有网页直连/Remote 只读请求都零写入，需要查宿主入口或提供对应合法拦截点；不能仅测聊天 Tool 就作此保证。

## 启动卡住的排查顺序

先保留现场，不自动取消或重启。查看本次任务 run.json 的 record/events、日志、已生成文件及时间；同时核对实际安装目录、版本和当前服务启动方式。终端无日志不等于任务没有日志：SDK 上报通常进任务记录。

| 现象 | 能得出的结论 | 下一步 |
|---|---|---|
| 只有 Run 的 request.json、manifest 和开始日志 | 尚无 Python 成功保存输入的证据 | 检查启动、通信、文件写入，不先归因于模型慢 |
| 进程存在 | OS 创建了进程 | 核对父子关系、argv、版本及归属，不把其他插件的 Python 算进来 |
| CPU 持续增长、没有模型请求 | 可能在导入/循环/错误处理 | 采集允许范围内的栈或诊断，不断言“正在等模型” |
| 已有准备确认和提取实体阶段 | 已通过启动并进入该阶段 | 查看首个 model_request、宿主模型日志及超时 |
| 只有日志处理器初始化异常 | 可能在主 try 外退出了后台协程 | 检查 job 终态、异常观察者及上层轮询 |
| Win32 5 / PermissionError | 对某个实际操作的权限拒绝 | 找到确切路径、进程令牌与调用，不直接判为宿主 bug |

Windows venv 启动器可能再派生实际 Python，看到两个 Python 并不等于两个任务。不同包、profile、source/tsx 与 built/lib 的解析路径也可能不同，必须核对正在运行的实现。

本次确认过：工作区根已有沙箱 SID/低完整性标签，实际 outputs/任务子目录却没有相应权限；根目录授权缓存跳过重做。随后仅收窄到任务目录的授权尝试也遭 SetNamedSecurityInfoW Win32 5 拒绝。该证据解释当时环境，不代表所有 DSH 安装都有相同故障。

诊断读取只需函数名、路径、状态等必要信息，不转储模型正文、环境凭据或进程全量内存。不能把修改源代码加日志说成“只读排查”；独立诊断子进程也需明确用途和输出目录。无法复现时报告已排除范围与缺失证据，不编造根因。

## 业务保持方面踩过的坑

- “保留全部缺失操作”的修正会改变原版覆盖操作提示的行为，进而影响用例生成、实体扩张和收敛；它不是单纯模型接入，应单独批准和验证。
- 把所有模块历史合并、顺手规范化实体名、改变分隔符/去重/错误回退，都可能悄悄改变算法。
- 方法判定 converged、成功输出 DOCX、内容完整正确是三件不同的事。实体/用例噪声可能进入文档，即使迭代收敛也要如实报告。
- 最终文档应承载用户需求；CRUD、PlantUML、模型往返、每轮缺口等可审计材料另外保存，不塞进主要文档正文。

## 进度显示方面踩过的坑

只报 stage 而省略 progress，网页可以显示“—”；启动设置过 0% 不会让后面自动计算。此版 Runtime 后续 reportProgress 没有 progress 时会删除旧值；其他版本要查实现。

有百分比需求时，按真实阶段及迭代上限分配权重，任务内单调递增；可选阶段跳过、提前收敛应跳到后续阶段，不倒退。模型调用期间不随时间虚增。不同项目采用不同权重，不机械复制 Req 的 38–78% 迭代区间。

主交付物生成、校验和登记前不报完成。插件报 100% 只说明插件流程到达交付点，Run 的 completed 仍由正常返回、结果校验和清理决定；失败/取消时保持真实状态，不能靠报 100% 掩盖。

## 足够而不过度的验证

默认小输入、模拟模型、有限超时；不默认执行半小时以上的完整算法或真实模型调用。根据改动选择以下层级，并分别报告证据：

| 层级 | 验证内容 | 不能据此宣称 |
|---|---|---|
| 源码/类型/构建 | 真正导出、注册、契约、打包内容 | 插件已经在网页成功运行 |
| 环境 probe/health | 解释器、依赖或后端服务启动 | 真实任务目录可写、算法正常 |
| 独立入口测试 | 正常 DSH Run 链＋真实 Python＋模拟业务/模型，文件登记和取消 | 原算法完整执行或真实模型兼容 |
| 真实工作区小测试 | 同一执行方式，在实际服务工作区下的新独立目录写文件 | 已验证真实 profile、远程浏览器和全算法 |
| 实际 profile/网页 | 授权后加载状态、正常调用、认证下载、终态 | 未执行过的其他模型或输入均可用 |
| 用户报告 | 明确标记用户反馈的运行成功 | Agent 亲自独立完成所有完整测试 |

针对本次迁移最有用的小测试：模型继承/独立指定、主聊天模型不变、阶段先于模型调用、启动确认超时、目录或日志不可写、首错不被落盘失败覆盖、取消停止自有进程、部分材料保留、最终 artifactId 和下载引用有效。选择与当前改动相关的几项，不每次重跑所有层级。

模拟算法生成的小 DOCX 只验证交付链，不要称为原算法业务验收。若已拿到真实模型的截断错误、空响应或不支持图片，保留失败语义，不用假内容凑成功产物。

## 构建与安装的坑

1. 本地目录安装可能是链接。改 package/lib 或构建已链接目录可触发 HMR、停用业务入口并中断运行任务；重启也会中断。**构建前查活动任务**，需要时先在未安装的副本构建验证，等用户安排更新；不能保证“只是 build，不影响任务”。
2. 核对安装的是项目根、release 目录还是 TGZ 的展开目录。源码改了不等于目标 lib 更新；构建过不等于 profile 正在使用这份构建。比较实际解析路径、版本和散列。
3. 业务插件需要 Runtime 服务；SDK 是开发依赖/可打包的库，不等于已经安装 Runtime 插件。Runtime 与业务插件需在同一 profile，目录不必相邻。
4. 本地目录链接安装后不要删除/移动目录。远程浏览器里的安装路径指 DSH 服务端磁盘，不会把浏览器电脑的目录上传。
5. `relinking ... requires a process restart` 表示包重新解析需要服务进程重启，不等于缺少 Python 或 Runtime，也不能靠刷新网页证明已加载。
6. 只有实际 schema 需要时才写允许名单、解释器和超时配置。安装不自动执行 pip；插件安装成功、Python 环境可用、业务任务成功分别验证。
7. 使用环境现有的构建方式；PowerShell 执行策略拦 npx.ps1/pnpm.ps1 时可使用 .cmd 入口，不改全局执行策略。不要照抄本机源码里的绝对路径。

用户 README 保持简短：用途与输入输出 → 服务端环境 → 安装 Runtime/业务插件 → 配置实际解释器 → 正常启动/查询/取消 → 文件位置与下载 → 已验证范围和常见报错。把长篇开发排查留给本参考资料，别要求用户理解所有内部实现才能安装。
